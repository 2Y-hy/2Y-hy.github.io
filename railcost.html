THE STARTING POINT

数字能加起来，
业务却未必算对。

预算与收入内部施工成本预算，不能当作对外合同收入。

采购与耗用买了多少、付了多少、实际用掉多少，是不同的事实。

原件与结果汇总有差异，必须保留来源并核对，不能直接把差额改平。

01 / DISCOVER

先还原工作现场，
再讨论软件功能。

从施工预算、现场备用金、采购台账和考勤工资等场景出发，梳理每一类记录代表什么，以及谁需要确认它。

需求起点 / 2026.11

关键判断

内部预算不等于合同价；台账登记不等于成本确认；缺少收入依据时，不输出确定利润。

具体推进

  • 盘点 Excel、PDF 图纸与附件结构，识别多工作表、公式、合并区域和图片引用。
  • 区分已知事实、需要人工确认的业务口径，以及未来版本想做的能力。
留下的产物原始需求 · 资料核查与导入映射 · 待核实事项清单

02 / DEFINE

把“大系统”，
拆成可检查的小交付。

先做本地单人使用的闭环，把预算、资金、材料和工资按依赖分批推进。

需求与计划 / 2026.11.03

关键判断

每一批都需要能运行、能操作、能检查；功能名称和空白页面不能代替交付。

具体推进

  • V1.0 先覆盖预算导入、版本、图纸复核与备份恢复。
  • V1.5 按 B01/B02 业务资金与台账、B03 材料、B04 工资逐步推进。
  • 将“重复导入、部分付款、更正、恢复”等场景写入验收计划。
留下的产物正式 PRD · 版本任务 · 验收场景与范围

03 / RESEARCH

先找成熟方案，
再判断哪些要定制。

对比 ERPNext、Odoo 和 FastAPI 官方全栈模板，考虑已有能力、适配成本与本机使用要求。

开源评估 / 2026.11.03

关键判断

完整 ERP 值得参考，但铁路工程口径、多模板 Excel 与本地 SQLite 仍需要适配。

采用的技术方向

React / TypeScript页面与业务交互FastAPI / Python接口与业务规则SQLite / Alembic本地存储与迁移Decimal / openpyxl金额与表格处理

选型文档推荐参考官方全栈模板并裁剪适配；不将模板本身描述为现成的工程成本系统。

留下的产物开源方案比较 · 技术架构 · 数据库设计

04 / MODEL

先让业务关系成立，
再让界面显示数字。

围绕来源、业务、资金和成本建立关联，规定什么可以确认、什么必须阻止、什么需要保留历史。

贯穿开发的业务规则

三条核心约束

  • 业务、付款、成本分开。付款不再产生一次成本，材料领用也不自动当作耗用。
  • 同一来源全局守恒。跨模块分配不能超量、超额；区间不重叠也要检查金额。
  • 更正留下历史。原件与已确认事实保留，采用显式冲正和替代。

05 / BUILD WITH AI

一批一批做，
每一批形成操作闭环。

向 Codex 提供业务要求和验收条件，在已有功能上推进实现，并用实际页面与数据检查结果。

阶段实现 / 2026.11.04—06

已推进的模块

  • 预算基础：Excel 映射与预览、预算版本、图纸复核、导出及备份。
  • 业务与资金：业务确认、应付、备用金、付款核销和台账候选核实。
  • 材料闭环：采购、收货、库存、耗用、退货与冲正。
  • 工资开发：考勤、工资批次、来源核实、付款与成本关联，仍待问题修复及验收。

06 / VERIFY

测试通过之后，
继续问：哪里还会错？

通过独立验收会话复验交付，既检查正常流程，也尝试重复提交、跨模块重复来源、异常恢复和合法业务误拦。

开发自测与独立验收分开

验证怎样展开

L1聚焦回归与类型检查L2相关模块与历史回归L3完整回归、构建与浏览器等门禁

再以 HTTP、浏览器、独立 SQL 和恢复重启核对结果。测试写入只在隔离环境，正式服务保持只读核查。

一次关键发现

B04 的固定门禁通过后，独立新增用例仍发现来源保护与合法凭证误拦问题，因此该批没有签收。

留下的产物测试结果 · 页面证据 · 数据核对 · 独立缺陷报告

07 / ITERATE

用反例改规则，
再把规则变成回归。

将验收发现的问题收敛到明确的修复范围，保留原失败证据，补上负向与合法正向用例，再按顺序复验。

问题 → 修复 → 回归 → 独立复验

B03 中的代表性迭代

同一原行在不同模块分别分配时，即使数量区间相邻，舍入后的金额仍可能累计超额。修复从单模块检查，推进到统一来源、数量与金额守恒。

完成的判断标准

既阻止重复和超额，也允许正确的尾差分配与合法相邻范围；不能只增加拦截而误伤正常业务。

留下的产物精准整改报告 · 正反例回归 · B03 第十一轮独立验收
